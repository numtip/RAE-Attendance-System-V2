## 2. Deliberately not done in #63

- **No controller or cookie plumbing.** Supplying a browser binding touches session semantics under MJU's
no-`state` constraint; that is an owner design decision. **The binding is inert until a caller passes it**, so
merged behaviour equals previous behaviour.
- **No Redis/SQL backend.** The seam and its contract exist; the deployment-specific implementation does not.
A multi-instance production deploy still needs one (tracked as **L-4** on the standard's side).

## 4. Risks

1. **The binding is not live.** A merged-but-unused capability can be mistaken for a fixed one. Nothing changes
   until `ssoController` supplies `browserBinding`; that is the next SSO PR, scoped separately.
2. **Single-process only.** The in-memory backend is bounded and reports `durable:false, shared:false`; a restart
   still drops outstanding login state unless a shared backend is wired.
3. **The national-ID P0 is unchanged.** Today's merge does not touch it; #60 remains the containment and the
   history exposure remains unremediated.
4. **Four SSO/DB PRs from 2026-10-21 are still open.** Merging #63 ahead of them was safe because it touched only
   the state store, but their review debt is real and unchanged.

## 5. Rollback

#63 changes no schema, no migration and no deployment target. Rollback is a code revert only:

```
git revert --no-edit d1e0240      # or `git revert -m 1 <squash commit>` on a branch + PR
```

No database action is required, and the Pages preview rebuilds from `main` on the next push. If the revert is
ever needed, the SSO state store returns to the previous in-memory implementation with identical behaviour.
